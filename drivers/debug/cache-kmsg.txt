Cache kernel log snapshots (CONFIG_SEC_CACHE_KMSG)
================================================

The built-in cache_kmsg thread takes a snapshot of the latest printk records
every two seconds, but writes only when the printk sequence has changed.
It starts at fs_initcall_sync, independently of Android services and adbd.
It retries a private ext4 mount of the J250F cache partition every 250 ms
until storage/device nodes are available. It does not wait for Android to
mount /cache. The private mount is not attached to Android's mount namespace;
the files are nevertheless visible when recovery mounts the same partition.
An already mounted ext4 superblock is reused by the VFS.

CONFIG_DEVTMPFS=y is required. The worker unshares its fs_struct, privately
opens devtmpfs, and uses its kernel-created /mmcblk0p46 node. It does not wait
for Android ueventd to create /dev/block nodes. Only the worker's root/pwd
change; Android's /dev, root, and mount namespace are left untouched.
CONFIG_DEVTMPFS_MOUNT remains disabled to avoid automatic namespace mounts.

Output: /cache/kernel-latest-0.log and /cache/kernel-latest-1.log
Each file contains up to 512 KiB of timestamped kernel messages. The files
alternate after successful writes; choose the newest timestamped content.
The other slot is not touched while a snapshot is being written. A failed
or interrupted write can leave that slot incomplete. A successful write is
truncated to the snapshot length and fsynced before switching slots.

The logger requires a writable ext4 cache filesystem, with at least 8 MiB
plus one snapshot available to the caller. It never formats or writes raw
block devices. Normal ext4 mount/journal recovery is allowed. It never forces
a readonly or corrupt filesystem writable. Failure transitions are reported
in printk as cache_kmsg messages; unavailable/readonly/full cache is retried.
Output files are created mode 0600. Symlinks, hardlinks, nonregular files and
a changed mount are rejected before writing file data.
Existing files are reused; nothing else in cache is deleted.

Limitations
-----------
* A failure before kernel initcalls or before storage/device nodes become
  available cannot be saved by this driver. A storage driver hang can also
  block mounting/writing. This is not a guarantee of universal capture.
* Panics/hangs/power loss can lose records since the most recent fsync.
  There is deliberately no filesystem-writing panic callback: filesystem
  and storage locks may already be held by the failing CPU.
* A filesystem/storage failure may prevent writing entirely. SELinux can
  also deny the thread access; this driver does not bypass policy.
* This is a diagnostic feature and adds flash writes. Disable it after
  diagnosing the port. It is not a replacement for ramoops/last_kmsg.
* New boots eventually replace both slots. Recover logs before repeatedly
  booting another kernel with this feature enabled.
* The private mount pins the filesystem while the diagnostic kernel runs.
  Do not format cache during that boot; use recovery without this feature
  for filesystem maintenance. This feature is J2Y18LTE-specific.

Recovery collection (read only):
  adb pull /cache/kernel-latest-0.log
  adb pull /cache/kernel-latest-1.log

The GitHub workflow verifies CONFIG_SEC_CACHE_KMSG=y and compiles the driver
as part of the normal J250F kernel build. Build artifacts are kernel-only;
they are not flashable boot images and must preserve the correct ramdisk.
Previous-boot crash records
---------------------------
After obtaining cache, the worker privately mounts pstore and copies known ramoops
records into /cache/previous-boot-NN-<pstore-name>, before live snapshots. Source
names follow this tree's fs/pstore/inode.c (console-ramoops has no numeric suffix).
Compressed dmesg records retain .enc.z and are not interpreted as plain text.
Each destination is created exclusively, checked as a single-link regular file,
and fsynced. Existing exports are never overwritten. Retention is bounded to 16
files per source name and the existing free-space reserve applies. Each record
is capped at 512 KiB; this device's configured ramoops records are 256 KiB.

This executes in normal process context, never in a panic callback. It cannot
preserve RAM across loss of power or export if the next kernel fails before the
cache worker runs. Recovery's empty pstore is not evidence that Android had no
ramoops records when recovery has no matching ramoops device.
